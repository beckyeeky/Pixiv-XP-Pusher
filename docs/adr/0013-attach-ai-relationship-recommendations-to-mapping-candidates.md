# Attach AI Relationship Recommendations to Tag Mapping Candidates

The Tag Relationship Judge reviews the existing Tag Mapping Candidate queue rather than creating a second semantic-candidate store. The authoritative candidate may carry nullable Embedding similarity evidence, so future Embedding candidate generators do not require another persistence model. The Judge uses the same configured `tag_mapping` LLM Model and persists each AI Relationship Recommendation with its model, versioned merge principles, and complete evidence snapshot. Freshness hashing covers stable semantic evidence such as tags, classifications, translations, explanations, proposal provenance, and optional Embedding similarity, while volatile Preference Profile weights remain in the audit snapshot and prompt without invalidating an otherwise unchanged identity judgment. Changed semantic evidence or principles makes an older recommendation ineligible for shortlist staging.

Candidate rows from different legacy sources that describe the same unordered tag pair form one review group. A current AI Relationship Recommendation owned by any row in that group is reused as the group's advisory result, so the same pair is not sent to the Tag Relationship Judge again merely because another provenance row exists.

High-confidence batch staging only marks the latest recommendation as `accept_equivalent` or `reject`; it does not change the candidate status and never writes `tag_aliases`. Equivalent staging additionally requires matching resolved categories, no risk flags, exact safe principle checks, and the existing candidate direction as canonical. Final activation remains an explicit human action through the authoritative Tag Mapping Candidate review flow, preserving ADR 0012.

The WebUI may turn that strict staging plan into one explicitly confirmed batch review. It must first preview the exact accept/reject counts and examples, bind confirmation to a freshness token, then apply the unchanged plan in one database transaction. Any stale recommendation, changed candidate, alias conflict, or blocked relationship cancels the transaction; blocked items remain in the ordinary manual queue. If the opposite equivalent alias is already active, accepting the redundant reverse candidate closes its review group while preserving the existing human-selected canonical direction instead of creating a cycle.
